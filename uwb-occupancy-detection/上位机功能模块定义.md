# uwb-occupancy-detection 上位机功能模块定义

> 目的：为后续重构提供一份模块边界说明书。描述基于对当前源码的通读，
> 给出每个模块的职责、涉及文件、关键类/函数、以及现有耦合问题。
> 本文件只是分析产物，不修改任何代码。

## 0. 项目定位

这是一套**车载乘员占用检测（CPD / Occupancy Detection）上位机软件**：

- 硬件：UWB/CIR 雷达（Calterah 系 MCU，中心频率 ~7.99 GHz，带宽 100 MHz），
  通过 UDP / CAN(CANFD) / 串口把**复数 CIR（channel impulse response）帧**发到上位机。
- 每个标准帧：`START(4B) + TX(1B) + RX(1B) + CIR(ft_len×4B) + STOP(4B)`，
  CIR 为 int16 IQ 交织的 32 tap 复数信号；天线规模 1~2 TX × 4 RX。
- 上位机做：接收 → 分帧 → 按 TX/RX 通道缓冲 → 去背景 → （范围-多普勒/
  距离-角度/热力图/点云）信号处理 → 检测乘员（EMPTY / CHILD / ADULT，或
  座位 IN/OUT）→ 界面可视化；同时支持录制 bin、离线回放、训练数据采集
  （BD 正样本触发）、模型推理（TFLite OA）、点云 JSON 导出。
- 配套的还有一批**离线脚本**（数据生成、PyTorch 训练、结果可视化）和
  两篇论文/一份厂商算法文档，它们不是上位机运行时的一部分，但共享
  协议/算法代码，重构时需一并考虑。

## 2. 模块定义

### M1 GUI 交互层（tkinter + matplotlib）

- 文件：`gui_main.py` 第 3527 行以后（`# 6. UI`）
- 关键类：
  - `PlotPanel(tk.Frame)`（~3599）：绘图面板。`init_layout(mode, params)` 按
    算法模式建子图（波形 / MUSIC+多普勒 / 点云+座位椭圆 / RA 热力图 /
    RA-OCCUPANCY 热力图+座位能量格+OA 按钮）；`update_data(mode, data)`
    按模式刷新画面；`_draw_seating_ellipses` 绘制座位椭圆；
    `_update_ra_occ_oa_filter` 实现 OA(IN/OUT) 滑窗滤波按钮显示。
  - `ControlPanel(tk.Frame)`（~4617）：左侧控制栏。IO 模式下拉
    （UDP/BD_UDP/BD_CAN/SERIAL/CAN/PLAYBACK）、算法下拉（11 种）、
    串口/UDP/CAN 参数、录制与回放设置、座位配置入口、开始/停止。
  - `AlgoSettingsDialog`（~3530）：`DEFAULT_ALGO_PARAMS` 参数的通用编辑弹窗。
  - `SeatConfigDialog`（~4394）：编辑 `SEAT-OCCUPANCY` 座位几何与阈值。
- 职责：人机交互、可视化、参数编辑；**不含**业务/算法逻辑（但当前与
  后端通过回调 + 全局 config 直连，耦合较深）。

### M2 应用编排层（主控制器 / 运行时）

- 文件：`gui_main.py`；`App` 类（~5233），主循环 `App.loop`（~5692）。
- 职责与关键逻辑：
  1. 组装：`RadarConfig`（dataclass 配置）、`RadarDataManager`、
     `AlgorithmProcessor`、两个占用检测器、`LiveRadarSource`/`FilePlaybackSource`。
  2. 状态机：`start()/stop()`、`update_layout(mode)`（切模式重建检测器、
     重置算法状态）、批量回放 `_start_next_file()`（换文件时重实例化
     数据管理器/算法处理器/检测器，即“全量状态复位”）。
  3. `loop()`：主线程 tick（约 20ms）：从 source 拉批量帧 →
     `RadarDataManager.process_frame()` → 按 `current_algo` 调用
     `AlgorithmProcessor.step_*()` → `PlotPanel.update_data()`。
  4. 录制 `start_recording`（bin + `.meta`）、回放进度、FPS 统计。
  5. RA-OCCUPANCY 专用：`_try_step_ra_occupancy` 节拍控制、
     `_ra_occ_run_model` TFLite OA 推理（懒加载解释器，输入为热力图样本）、
     BD_UDP/BD_CAN 模式下的“阳性触发计数 + 自动保存去背景样本”
     （`_bd_*` 系列，采集训练正样本用）、回放样本导出。
  6. 点云 JSON 导出 `save_pc_to_json`（PLAYBACK + export_pc_json 时）。
- 现状：App 同时承担编排、采集触发、模型推理、样本采集、导出等，
  是重构时最需要拆解的“上帝类”。

### M3 数据采集 / 传输层（数据入口）

| 子模块 | 文件 | 说明 |
|---|---|---|
| UDP 采集 | `UDP_data_listen.py` `UDPFrameServer` | 绑定 UDP 端口；按 `total_tx×total_rx×bytes_per_channel` 校验；切出每 TX/RX 的 CIR 并封装成标准帧入队 |
| CAN 采集 | `CAN_data_listen.py` `CANFrameServer` | 读 CAN 报文(0x100)→拼 320B 传输单元→按 UCI 同步头 `0f001001` 找包→按 idx/PACKET_CNT(4) 组装“完整快照”→按 MCU（Calterah / 29D6）天线映射拆出标准帧入队；`radar_hardware_init()` 发送雷达启动命令序列 |
| 串口采集 | `gui_main.py` `LiveRadarSource._io_loop`（SERIAL 分支）+ `frame_sync.py` | 串口字节流经 `FrameSyncBuffer.feed` 分帧（找帧头 + 定长切帧），多帧暂存 `_serial_pending` 不丢帧 |
| 实时源封装 | `gui_main.py` `LiveRadarSource`（~3360） | 按 connection_mode 启动对应 server，后台线程收帧 → 解析 → `data_queue`；含录制写盘与 FPS 统计 |
| 回放源 | `gui_main.py` `FilePlaybackSource`（~3452） | 按 `playback_duration` 换算 FPS 匀速读 bin → 解析 → 入队，提供进度 |
| 录制 | `LiveRadarSource.start_recording/stop_recording` | 原始标准帧写 `.bin` + 配置 `.meta` |

### M4 协议与分帧层

- 文件：`gui_main.py` `RadarProtocol`（~544）；`frame_sync.py` `FrameSyncBuffer`；
  `generator.py` 内另有一份 `RadarProtocol`（离线读取时用，**同逻辑重复实现**）。
- 职责：`RadarProtocol.update_protocol(ft_len)` 按 tap 数重算
  CIR 字节数与帧长；`parse_frame` 校验帧头/帧长并解析出
  `(tx, rx, complex_cir)`；`FrameSyncBuffer` 为传输无关的字节流→完整帧切分器
  （串口/CAN 重组流/文件流通用）。
- 现状：协议常量与解析逻辑在 `gui_main.py` / `generator.py` 两处重复，
  且 `RadarConfig` 与 `ConfigAdapter` 为兼容各 server 的字段名做了桥接。

### M5 硬件设备驱动层（CAN 双厂商抽象）

- 统一入口：`device_management.py`——`DevicePara`（模块级全局句柄）、
  `init_device("ZLGCAN"|"TOOMOSS")`、`deinit_device`、`CAN_SendMsg`、`CAN_GetMsg`。
- ZLG 路径：`zlgcan.py`——`zlgcan.dll` 的 ctypes 封装（`ZCAN` 类 + 结构体 +
  `zlgcan_init/zlgcan_send/ZLGread_msg` 等便捷函数）。
- 图莫斯路径：`usb_device.py`（USB2XXX 设备 API）、`usb2canfd.py`
  （CANFD 结构体与收发 API）、`canfd.py`（`canfd_init` + 发送雷达 CPD
  命令报文 + `CPD_data` 解码辅助 + 参数表 PARA/NUM_TYPE）。
- 雷达启动指令：`radar_config.py`——UCI GID/OID 常量与
  device_reset/session_init/set_app_config/set_radar_config/range_start/stop
  命令字节序列。
- 静态资源：`kerneldlls/`（ZLG 全系 DLL+XML+ZPS 子目录）、`libs/`
  （图莫斯 USB2XXX 多平台 .so/.dll）、根目录 `zlgcan.dll/.lib`。
- 现状：两个厂商接口形状不同（句柄/缓冲结构/返回值），由
  `device_management` 用全局状态 + 分支收敛；`canfd.py` 与 `zlgcan.py`
  还夹杂 CPD 报文语义（发送内容）与纯驱动（怎么发）两层内容。

### M6 数据管理与预处理层

- 文件：`gui_main.py`（`# 3. Data Manager` 起，~659）与 `generator.py`
  （同逻辑重复实现）；类：`FixedBuffer`、`BackgroundRemoval`、`RadarDataManager`。
- 职责：
  - 按 (tx, rx) 通道维护 raw/complex/abs 三类 `deque(maxlen)` 快照缓冲；
  - `BackgroundRemoval`：指数滑动平均背景（复数 + 幅值）参考与差分
    （去静止杂波/直达波）；
  - `process_frame`：入 raw 缓冲 → 去背景 → 入 complex/abs 缓冲；
  - `get_all_snapshot_as_array`：取所有通道对齐到最小长度，
    输出 `(rx, tx, ft, time)` 复数/浮点张量，供算法批量处理。
- 备注：这是**上位机实时链路与离线 bin 生成共用的核心数据结构**，
  目前靠复制粘贴保持同步，重构应合并为单一模块。

### M7 信号处理 / 算法层

- 文件：`gui_main.py` `AlgorithmProcessor`（~791，内部约 2300 行）。
- 公共能力（一次初始化、按算法复用）：
  - 初始化 steering：DBF/Capon/MUSIC 角度向量、虚拟阵列、
    相位标定（`ant_calib_phase`）、距离-角度网格、RF 参数换算。
  - 帧批处理：CIR 组合 `cir_combine_num`、range FFT、Doppler FFT
    （Chebyshev 窗、DC 去除）、泄漏 offset、通道合并、范围 bin 截取。
- 各模式算法入口（GUI 下拉的 11 种算法）与职责：

| 模式 | 入口 | 职责 |
|---|---|---|
| PLOT | `step_waveform` | 原始 CIR 波形/饱和显示 |
| 2D-MUSIC | `step_2d_music` | 多普勒谱→目标 tap→MUSIC 距离-角度成像→融合定位 + 呼吸特征 |
| POINT-CLOUD | `step_point_cloud` | Range-Doppler CA-CFAR → 角度（MUSIC/DBF/FFT）→ 点云 |
| POINT-CLOUD-OPTIMIZED | `step_point_cloud_optimized` | 优化参数版（多普勒寻峰、subbin 细化等） |
| POINT-CLOUD-PAPER | `step_point_cloud_paper` | 复现论文多级 CFAR：NVE 归一化→逐多普勒 1D Range CFAR→粗角度峰→Zoom-in 细化 |
| POINT-CLOUD-DUBHE | `step_point_cloud_dubhe` | 镜像厂商 Dubhe CPD 官方算法（Doppler 滑窗、动态 CFAR 阈值等） |
| RA-CFAR | `step_point_cloud_ra_cfar` | Range-Azimuth 二维 CA-CFAR（或论文 two-pass）→ 点云 |
| RA-HEATMAP | `step_ra_heatmap_view` | Capon RA 热力图显示 |
| RA-OCCUPANCY | `step_ra_occupancy` | Capon RA 热力图 → 去背景 RMS + 平滑 → 座位椭圆能量 → （可选）OA 模型 |
| ANGLE-SPECTRUM | `step_angle_spectrum_view` | 角度谱视图 |
| AS-RAW | `step_angle_spectrum_raw` | 原始角度谱视图 |

- 现状：所有模式塞在一个巨型类里，靠 `self.config.algo_params[mode]`
  大字典驱动分支；每模式处理链的长短差异很大（几百行 vs 几十行），
  是“按模式拆分处理器”的首选重构目标。

### M8 占用决策层（输出语义）

- 点云→座位占用：`SeatOccupancyDetector`（`gui_main.py` ~3121），
  实现论文公式 (12)-(16)：椭圆归属 → 点数/分散度归一化 f_k → 阈值 →
  滑窗平滑 + hold 保持，输出各座位 0/1。
- 热力图能量→三态：`RAOccupancyDetector`（~3227），输入每座位
  `{main, child_special}` 能量，主区成人双条件 + 小孩区间、角坑特判区，
  输出 `state: 0=EMPTY / 1=CHILD / 2=ADULT` 与 occupancy 0/1。
- 座位几何/阈值：`DEFAULT_ALGO_PARAMS['SEAT-OCCUPANCY']`（4/5 座，
  主椭圆 `main`、特判椭圆 `child_special`、`smooth_window/hold_time_sec`）。
- 呼吸特征：`breathe.py` `find_breathing_feature`——多普勒 FFT 幅度谱上
  指定频率/路径范围找呼吸能量（复现 C 代码），供 2D-MUSIC/点云显示。
- OA 网络推理（RA-OCCUPANCY 可选）：TFLite 解释器在 `App` 内
  （`_ra_occ_get_interpreter/_ra_occ_run_model`，~5548+），输入标准化后的
  热力图样本，输出 label/score，驱动 OA(IN/OUT) 显示与 BD 采集触发。
- 现状：两个 Detector 已经是“输入数据→输出状态”的纯逻辑类（相对独立、
  可单测），是当前代码里边界最清晰、最适合先抽出重用的部分；但 OA
  模型推理/样本装配逻辑仍嵌在 App/PlotPanel/AlgorithmProcessor 中。

## 3. 关键数据流（重构必须保持的运行时契约）

1. **实时接收**：`UDPFrameServer / CANFrameServer`（或串口+FrameSyncBuffer）
   产出**标准帧 bytes** → `LiveRadarSource` 解析为 `(tx, rx, complex_cir, raw)`
   入队 → `App.loop` 批量取帧 → `RadarDataManager.process_frame`（去背景+缓冲）
   → 缓冲满触发对应 `AlgorithmProcessor.step_*()` → `PlotPanel.update_data()`。
2. **RA-OCCUPANCY 特有节拍**：最后一个 TX/RX 通道到达时才推进一个
   “快照”（snapshot）→ 满 `snapshots` 帧后按 stride 算一次 RA 热力图 →
   座位能量 → `RAOccupancyDetector` 三态 → 可选 TFLite OA → 界面
   OA 按钮 + 座位色块。
3. **录制**：标准帧在入队前原样写 `.bin`（配 `.meta` 记录配置）。
4. **回放**：`FilePlaybackSource` 按目标时长换算 FPS 匀速重放 `.bin`，
   与实时共用同一后续链路；批量回放时每换一个文件就
   “重建 DataManager/AlgoProcessor/Detector + 清空各类缓冲”。
5. **BD 模式（BD_UDP/BD_CAN）**：复用 UDP/CAN 接收，附加“OA 模型得分
   达到阈值 → 阳性触发计数 → 把该窗口去背景 CIR 保存成 bin/样本”
   的数据采集行为（供离线训练正样本）。

## 4. 现有耦合与重复清单（重构切入点）

1. **`gui_main.py` 单文件五合一**：UI / 协议 / 数据管理 / 全部算法 /
   编排，共 ~5800 行。其中 `AlgorithmProcessor` ~2300 行、`PlotPanel`
   ~800 行、App+ControlPanel ~1300 行。
2. **代码复制**：`RadarProtocol`、`FixedBuffer`、`BackgroundRemoval`、
   `RadarDataManager`、去背景/RA 热力图处理在 `gui_main.py` 与
   `generator.py` 各一份（离线工具与实时链路共享逻辑却未共享代码）。
   `util.py` 与 gui_main 内的 MDL/CFAR 也存在本地副本。
3. **配置体系脆弱**：`DEFAULT_ALGO_PARAMS` / `ANTENNA_LAYOUTS` 硬编码为
   巨型 dict；GUI 与 `generator.py` 各维护一套默认参数；`ConfigAdapter`
   仅为字段命名差异做桥接；无参数 schema/校验/版本。
4. **状态复位分散**：检测器重建与缓冲清空散落在 `App.update_layout`、
   `App.start`、`_start_next_file` 等处，容易漏复位。
5. **驱动层与业务混写**：`device_management` 用模块级全局 `DevicePara` +
   `import *` 暴露；`canfd.py`/`zlgcan.py` 同时含“厂商 API 封装”与
   “CPD/雷达报文语义”。
6. **模型推理与采集耦合在编排层**：TFLite 解释器管理、样本装配、
   BD 阳性触发、样本落盘都在 `App`/`PlotPanel` 内，无法脱离 GUI 复用。

## 5. 建议的目标模块结构（重构方向草案）

```text
uwb_occupancy/
├── app/                  # 入口 + GUI 壳
│   ├── main.py           # tk 启动
│   ├── control_panel.py  # 左侧控制栏
│   ├── plot_panel.py     # 可视化
│   └── dialogs.py        # Algo/Seat 配置弹窗
├── orchestrator.py       # App.loop / start-stop / 回放队列 / 录制编排
├── acquisition/          # M3~M5
│   ├── protocol.py       # RadarProtocol / 标准帧编解码（唯一实现）
│   ├── frame_sync.py
│   ├── sources.py        # Live / FilePlayback / 录制
│   ├── servers/          # UDPFrameServer / CANFrameServer
│   └── drivers/          # zlg / tumosi / device_management + 指令表
├── pipeline/             # M6
│   ├── data_manager.py   # RadarDataManager / BackgroundRemoval / 缓冲
├── algorithms/           # M7~M8
│   ├── common.py         # FFT/doppler/steering/校准 公共件
│   ├── processors/       # 每模式一个 processor（点云/论文/Dubhe/RA-*）
│   ├── detectors/        # SeatOccupancyDetector / RAOccupancyDetector
│   ├── breathing.py      # breathe
│   └── math_utils.py     # util.py 归类（CFAR/MUSIC/寻峰…）
├── models/               # OA/BD 推理封装（interpreter 生命周期+前后处理）
├── config/               # 布局/算法/座位默认参数 → json/yaml + schema
└── offline/              # M10~M11 工具脚本（可独立运行，import 共享库）
```

> 拆分顺序建议：① 先抽协议+数据管理（消除 gui_main/generator 重复）；
> ② 把两个 Detector 与 TFLite 推理封装成独立服务；③ 按模式把
> AlgorithmProcessor 拆成多个 processor；④ 参数外部化；⑤ 再动 UI。
